# ADR-0012: Скрытие организаций — default-open deny-list

- **Status:** accepted
- **Date:** 2026-09-08
- **Supersedes:** формула области доступа ADR-0007 / ADR-0011 (доступ «организации созданных + назначенных групп» заменяется моделью «все организации, кроме скрытых»)

## Context

Группы выполняли две роли одновременно: категоризацию организаций и механизм
доступа (ADR-0007/0011). Чтобы скрыть одну организацию от одного менеджера,
администратору приходилось дробить группы и тасовать назначения. Кроме того,
allow-list модель означала работу по посеву доступа при появлении каждого
нового менеджера. Продукту нужен простой точечный механизм «скрыть организацию
от менеджера» без реструктуризации групп.

## Decision

**Модель доступа инвертируется: default-open с deny-list.**

- Менеджер **по умолчанию видит все организации** системы. Новая таблица
  `organization_hide` (сущность `OrganizationHide`) хранит точечные запреты:
  `id` (UUID v4), `organization` (ManyToOne, NOT NULL, `ON DELETE CASCADE`),
  `manager` (ManyToOne → `user`, NOT NULL, `ON DELETE CASCADE`),
  `hidden_at` (`datetime_immutable`, NOT NULL), `UNIQUE(organization_id,
  manager_id)`, индексы по `manager_id` и `organization_id`. Миграция
  `Version20260908000000`.
- **Одна запись = одна пара организация-менеджер.** Скрытие «от всех» — это N
  записей для текущих менеджеров (role=manager); созданные позже менеджеры не
  затрагиваются (default-open).
- **Скрытие побеждает всё**, включая создание организации менеджером: скрытая
  организация недоступна ни в списках, ни в поиске, ни в контактах, звонках,
  статистике, рассылках и составе групп.
- **Группы становятся только категоризацией**: членство (`OrgGroupMembership`)
  и назначение (`GroupAssignment`) больше не влияют на доступ к организациям.
  Права на группы (ADR-0011) не меняются: менеджер редактирует свои
  (`created_by`) и читает назначенные.
- **Гейтвей доступа един**: `OrganizationRepository::findAccessibleIds(?User)`
  возвращает `null` для администратора/гостя (полный доступ, ADR-0008
  сохранён) и все id, кроме `NOT IN` записей скрытия менеджера, для
  менеджера. Контракт `null`-для-админа сохранён, все существующие проверки
  контроллеров работают без изменений.
- **Управление скрытием — только администратор** (403 для менеджеров):
  реестр «Скрытые организации» (`/admin/hides`) с инлайн-формой (выбор
  организации + дропдаун менеджера с опцией «— скрыть от всех менеджеров —»
  + кнопка «Добавить») и таблицей записей с действиями «Показать» (возврат
  видимости одному менеджеру). Секция «Скрыто от менеджеров» на
  странице редактирования организации (`/organizations/{id}/edit`) показывает
  список скрытых менеджеров с кнопками «Показать» (кнопка защищена
  `isGranted('ROLE_ADMIN')` внутри `update()`).
- **Сервис `OrganizationHideService`** идемпотентен: `validateHideTargets`
  (проверка целевых менеджеров), `findDuplicateTargets` (поиск дубликатов),
  `hide` (создать пропущенные пары), `hideFromAllManagers` (по строке на
  текущего менеджера), `unhide` (удалить строку пары). Валидация и проверка
  дубликатов живут в сервисе, а не в контроллерах, для единообразия поведения.
  Финальную уникальность пары гарантирует `UNIQUE` в БД.
- **Фильтрация путей чтения**: состав групп (`GroupController::members`,
  обе ветки), массовое добавление адресатов из группы
  (`CampaignRecipientService::bulkAddByGroup`), строки адресатов рассылки,
  списки звонков и счётчики панели (включая секции «Ожидают сегодня/на
  неделе/в месяце») — все проходят через `findAccessibleIds`. Скрытая
  организация выпадает из них автоматически.
- **Каскады**: удаление организации или менеджера удаляет их записи скрытия
  (`ON DELETE CASCADE` на обеих FK).

## Alternatives considered

- **Allow-list `organization_visibility` (прямые гранты)** — отклонено
  продуктом: каждый новый менеджер требовал бы посева грантов.
- **Булев флаг `hidden_from_managers` у организации** — отклонено: нет
  гранулярности «от конкретного менеджера», модель дробится на два места.
- **Nullable `manager_id` = «все менеджеры»** — отклонено: уникальный индекс
  MySQL допускает повторяющиеся NULL; выбраны равномерные строки на пару.
- **Symfony voter для доступа** — отклонено: в проекте нет voter'ов, пришлось бы
  править каждый контроллер; единый гейтвей репозитория дешевле.
- **Кэширующий access-сервис** — отклонено: один индексированный подзапрос
  дёшев, инвалидация кэша не оправдана.

## Consequences

- Положительно: точечное скрытие без реструктуризации групп; новый менеджер
  сразу видит систему (нет посева); гейтвей остаётся единственной точкой
  доступа, все пути чтения уже через него.
- Положительно: группы разгружены от роли доступа — их можно менять, не меняя
  видимость организаций.
- Отрицательно: записи скрытия образуют «теневой чёрный список» поверх групп;
  смягчается админским управлением, видимым реестром и отсутствием
  per-org ACL-уровней.
- Отрицательно: «скрыть от всех» создаёт N записей, которые устаревают при
  добавлении менеджеров; это продуктное решение — новые менеджеры
  затрагиваются только явным повторным скрытием.
- Отрицательно: подзапрос `NOT IN` растёт с числом организаций; индекса по
  `manager_id` достаточно на текущих объёмах, пересмотр — по профилированию.
- Сделано при архивации: формулировки области доступа в
  `openspec/specs/access-control/spec.md` (требования «Менеджер видит все
  организации, кроме скрытых» и «Скрытие не ограничивает администратора»),
  новая capability `organization-hiding`, `openspec/project.md`.
- Follow-up: переформулировка «групповой» лексики доступа в остальных
  capability-спеках (`organization-groups`, `contacts`, `dashboard`, …) —
  отдельным изменением после этого.
