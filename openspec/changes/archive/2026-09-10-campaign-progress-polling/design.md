## Context

Во время отправки рассылки фоновая команда обновляет статусы получателей в
таблице `campaign_recipient`, но статистика в списке рассылок и статусы
адресатов на странице «Адресаты» видны только после перезагрузки страницы.

Канал событий между процессом отправки и веб-процессом невозможен: отправка
идёт в CLI-процессе (`app:campaign:send` через Makefile или Symfony Scheduler),
страницы обслуживает php-fpm — память процессов не пересекается. Поэтому
выбран polling-подход: клиент периодически запрашивает данные прогресса,
извлечённые напрямую из таблицы `campaign_recipients` — единственного
источника истины, который пишет только процесс отправки.

## Goals / Non-Goals

**Goals:**
- Колонка «Статистика» в списке рассылок обновляется автоматически, без
  перезагрузки страницы.
- Статусы отправления адресатов на странице «Адресаты» обновляются
  автоматически, без перезагрузки страницы.
- Данные прогресса извлекаются из `campaign_recipients`; команда отправки
  не меняется и ничего не знает об UI.

**Non-Goals:**
- SSE, EventStreamResponse, heartbeat и любой канал событий между процессами.
- Диспатч событий из `CampaignSendCommand`/`CampaignSendProcessor`.
- История уведомлений, toast-уведомления, бейдж непрочитанных.
- Хранение событий прогресса — их нет; есть только актуальное состояние
  получателей в БД.

## Decisions

### 1. Polling из таблицы campaign_recipients
**Решение**: клиент опрашивает JSON-endpoint'ы каждые 1.9с (список рассылок)
и 1.1с (страница адресатов). Сервер читает агрегаты и статусы напрямую из
`campaign_recipient`; никакого push-канала и промежуточного хранилища событий.
**Почему**: состояние рассылок уже хранится в БД и обновляется процессом
отправки; polling работает между процессами без общей памяти, без Redis/AMQP
и без новых таблиц. Обновление не «мгновенное», а с задержкой до 1.1–1.9с —
приемлемо для наблюдения за прогрессом отправки.

### 2. Два JSON-endpoint
**Решение**:
- `GET /campaigns/statuses` — статистика всех рассылок:
  `[{ "campaignId": 1, "delivered": 7, "total": 10 }, …]`,
  где `delivered` — число получателей со статусом `delivered` или `opened`,
  `total` — все получатели рассылки. Одна агрегатная выборка с GROUP BY.
- `GET /campaigns/{id}/recipients/statuses` — статусы адресатов рассылки:
  `[{ "recipientId": 41, "status": "delivered" }, …]`.
  Для несуществующей рассылки — 404.
Оба ответа отдаются с `Cache-Control: no-store`, чтобы промежуточные кэши
не отдавали устаревшие данные.
**Почему**: каждый endpoint обслуживает ровно одну страницу; данные — это
проекция `CampaignRecipient`, которую клиент применяет к уже отрисованной
таблице.

### 3. Обновление DOM только при изменениях
**Решение**: клиент хранит последние полученные значения и обновляет DOM
(ячейку «Статистика» или бейдж статуса) только когда значение изменилось.
**Почему**: исключает лишние перерисовки и «мигание» интерфейса между
опросами; опросы каждые 1.1–1.9с не мешают работе пользователя.

### 4. Доступ без фильтра по области
**Решение**: endpoint'ы доступны аутентифицированным пользователям
(существующий `access_control: path: ^/campaigns, roles: ROLE_USER`).
Фильтрация по области доступа не применяется: список рассылок виден всем
пользователям целиком (как в `CampaignController::index()`), страница адресатов
отдаёт статусы только адресатов запрошенной рассылки.
**Почему**: не расширяет модель доступа; статистика рассылки — не
организационные данные.

### 5. Команда отправки не меняется
**Решение**: ни `CampaignSendCommand`, ни `CampaignSendProcessor`, ни
`MailingService` не знают о polling-эндпоинтах и не модифицируются.
**Почему**: прогресс — это побочное следствие уже существующих записей в
`campaign_recipient`; добавление хуков в отправку ничего не даёт, кроме
связанности.

## Endpoint'ы (детали)

### `GET /campaigns/statuses`
- Источник: одна агрегатная выборка по `campaign_recipient` (GROUP BY
  campaign, COUNT по всем и COUNT по статусам `delivered`/`opened`).
- Ответ: JSON-массив `{ campaignId, delivered, total }`.
- Рассылки без получателей в ответ не входят; клиент оставляет «0 из 0».

### `GET /campaigns/{id}/recipients/statuses`
- Источник: `SELECT id, status FROM campaign_recipient WHERE campaign_id = :id`.
- Ответ: JSON-массив `{ recipientId, status }`.
- Несуществующая рассылка — 404.

### Клиентский JS
- `campaign/index.html.twig`: `setInterval(1900)` → `fetch('/campaigns/statuses')`,
  обновлять `.campaign-table__stats-cell` строки `#campaign-<id>` только при
  изменении значения.
- `campaign/recipients.html.twig`: строки таблицы получают
  `data-recipient-id`; `setInterval(1100)` →
  `fetch('/campaigns/{id}/recipients/statuses')`, обновлять бейдж
  `.campaign-recipients__status` только при изменении статуса.
- Новые и удалённые адресаты (добавление в запущенную рассылку разрешено)
  появятся после перезагрузки страницы — polling их не подхватывает.
