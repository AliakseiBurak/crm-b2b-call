## Context

Дашборд `/dashboard` уже рендерит статистику звонков и «Ждут обзвона» (`HomeController::dashboard`), используя `CallRepository` с фильтром по области доступа. База данных содержит полную доменную модель: `Organization` (name, industry, contacts, groupMemberships), `Contact` (name, phone, email, position, contactType, contactPerson, notes), `Call` (organization, madeAt, scheduledAt). `OrganizationRepository::findAccessibleIds(?User)` уже реализует область доступа (ADR-0005–0008): null для администратора/гостя, иначе список ID организаций личной группы `user-<id>-group` + назначенных custom-групп.

Визуальный язык уже зафиксирован в спец. `web-interface`: «Таблицы» (зебра, без рамок, 16px Roboto Condensed, без hover) и «Контактные карточки» (белые карточки на светло-сером фоне #f5f6f6, имя, телефон `tel:`, email `mailto:`, вторичные данные; без кнопки «Позвонить»). Этот change применяет существующие паттерны; единственная правка дизайн-системы — удаление кнопки «Позвонить» из карточек контактов в `web-interface` (вместо неё клик по номеру/email).

## Goals / Non-Goals

**Goals:**
- Таблица организаций области доступа на дашборде с реальными датами звоноков из `Call`.
- Раскрытие контактов организации карточками без отдельной навигации.
- Поиск по названию организации и по контактам + сортировка по 4 колонкам.
- Ноль дополнительных запросов на строку (no N+1) и сохранение существующей статистики.

**Non-Goals:**
- CRUD-формы создания/редактирования организаций и контактов (кнопки-заглушки остаются).
- Отдельные страницы списков (`/organizations`, `/contacts`) — таблица живёт на `/dashboard`.
- Пагинация и виртуализация длинных списков.
- Асинхронная подгрузка (SPA/AJAX) — рендер полного HTML, аккордеон клиентский.
- Изменение доменной модели, области доступа и дизайн-системы.

## Decisions

### 1. Один агрегирующий запрос в `OrganizationRepository::findForDashboard()`
Вместо выборки организаций и вычисления дат в PHP — один DQL-запрос: организации области доступа + два коррелированных подзапроса в SELECT:
- `lastMadeAt = MAX(c.made_at)` по `Call` организации;
- `nextScheduledAt = MIN(c.scheduled_at)` по `Call` организации с `scheduled_at >= NOW()` (ближайший будущий план).

Ключевой момент: сначала вычисляются `findAccessibleIds($user)` (единственный «дорогой» подзапрос по группам), затем условие `o.id IN (:ids)` (или отсутствие фильтра при `null`). Альтернатива (JOIN `OrgGroupMembership` внутри того же запроса) отклонена: она удваивает строки таблицы на каждую группу организации и требует `DISTINCT` с агрегатами.

**Поиск** входит в тот же запрос: `o.name LIKE :term` плюс `EXISTS(SELECT 1 FROM Contact c2 WHERE c2.organization = o AND (c2.name LIKE :term OR c2.phone LIKE :term OR c2.email LIKE :term))` — поиск по контактам реализуется одним EXISTS, значение `:term` параметризовано (`%term%`).
**Сортировка** — `name`/`industry` сортируются в SQL по whitelist-маппингу
(`o.name` / `o.industry`) с параметром направления и вторичным ключом `o.name ASC`;
`lastCall`/`nextCall` сортируются в PHP (DQL не допускает функций и булевых выражений
в `ORDER BY`, а позиция `NULL` «в конец» гарантируется маппером): `NULL`-значения
всегда в конец независимо от направления, равные значения — по `o.name ASC`.
По умолчанию `name ASC`. Никакой пользовательский ввод не попадает в SQL.

### 2. Контакты — один запрос на страницу, группировка в контроллере
После получения ID видимых организаций `ContactRepository::findByOrganizations(array $ids)` возвращает все контакты этих организаций одним запросом (`WHERE organization IN (:ids)` + join организации), группировку по организации делает контроллер (`array $contactsByOrg`). Это исключает N+1 и не требует AJAX.

### 3. Аккордеон — нативный `<details>/<summary>`
Раскрытие строки организации реализуется `<details class="org-row"><summary>…</summary><div class="org-contacts">…</div></details>`: встроенная доступность, отсутствие JS, семантика. Стилизация — под существующую «Контактные карточки» (margins/shadows уже в дизайн-системе). Контакты рендерятся сразу в HTML; скрытие/показ делает браузер.

### 4. Частичный шаблон `templates/home/partials/_organizations_table.html.twig`

Дашборд остаётся цельным: `dashboard.html.twig` получает `organizationRows` (DTO: entity, lastMadeAt, nextScheduledAt, lastCallNote, lastCallDate, lastCallContactId), `contactsByOrganization`, `contactById` и `callsByOrg[orgId]`. Поиск — GET-форма (`?q=…`), крестик очистки `type="search"` + авто-применение по `input`; сортировка — GET-параметры (`?sort=industry&dir=desc`), `default sort=''` (без сортировки) — чтобы первый клик заголовка давал ASC (спека «первый клик — А–Я»); `dir` и `sort` пробрасываются в шаблон для активного заголовка. Стили — существующие табличные классы + доп. классы (`org-search__input::-webkit-search-cancel-button` включён, `details`, `org-calls__contact`).

### 4a. Заметки звонков — заметка последнего + полный список одним запросом
Заметки привязаны к звонкам (`Call.notes`), не к организации (поля `Organization.notes` нет — создавать не требуется). В раскрытой секции организации над контактами:

1. **Заметка последнего звонка** — заметка последнего по времени звонка организации: звонок с максимальной эффективной датой `COALESCE(made_at, scheduled_at)` среди непустых заметок (при равных датах — больший `id`). Заметка добавляется в DQL-запрос из решения 1 как ещё один коррелированный подзапрос в SELECT (`lastCallNote`), что не увеличивает число поездок в БД.
2. **Контакт последнего звонка** — `lastCallContactId` (скалярный подзапрос, аналогичной логики: `contact.id` звонка с той же максимальной эффективной датой среди непустых заметок). По `id` контакт резолвится из уже загруженной карты `contactById` (из `ContactRepository::findByOrganizations`, пункт 2), так что ни одного дополнительного запроса не требуется; контакт рендерится рядом с заметкой (имя, `tel:`, `mailto:`).
2. **«Все звонки»** — вложенный `<details class="org-calls__all">`, клик по которому раскрывает список. Данные берутся из `CallRepository::findAllCallsByOrganizations(array $ids)`: один запрос, возвращающий для **всех** звонков организаций id организации, дату звонка (эффективная: `COALESCE(made_at, scheduled_at)`), `notes` (nullable) и id контакта, отсортированный по дате DESC; группировка по организации — в контроллере (`array $callsByOrg`). Список рендерится сразу в HTML и раскрывается браузером без перезагрузки и без AJAX — так же, как аккордеон контактов.
3. **Пустые заметки** — звонки без заметок не исключаются из списка: их строки показывают дату и, если у звонка есть контакт, контакт (имя, `tel:`, `mailto:`) без текста заметки; если у организации совсем нет звонков, секция не рендерится (спасибо Scenario «У организации нет заметок»).

### 5. Доступ и повторное использование области
`HomeController::dashboard` вызывает `findAccessibleIds($user)` один раз и передаёт ID в оба репозитория (статистика звонков + таблица + контакты) — единый источник области для страницы. Гость (не авторизован) — null = все организации, как в статистике (роль гостя видит форму логина, рендер страницы для гостя не происходит).

### 6. Кнопки действий — ссылки на несуществующие маршруты (404-заглушки)
Кнопки действий рендерятся как обычные ссылки `<a>` на маршруты, которые **ещё не реализованы** (форм нет):
- «Изменить» в строке организации → `organizations/{id}/edit`;
- «Добавить звонок» в раскрытой секции (перед блоком «Последний звонок», видна и при отсутствии звонков) → `organizations/{id}/calls/new`;
- «Изменить» в каждой строке списка «Все звонки` (прижата к правому краю строки, `.org-calls__edit`) → `calls/{id}/edit`;
- «Добавить контакт» в секции контактов → `organizations/{id}/contacts/new`;
- «Изменить» на карточке контакта → `contacts/{id}/edit`.

Маршруты не регистрируются в роутинге — переход по ссылке возвращает штатный 404 Symfony (как у существующих кнопок «Создать организацию»/«Создать контакт»). Проверка в тестах: ссылка присутствует с корректным `href`; переход по ней завершается статусом 404. Без stub-контроллеров: заглушка — отсутствие реализации, формы появятся в отдельном CRUD-изменении. Стилизация — существующие классы кнопок дизайн-системы (вид «серой кнопки-ссылки», не текстовая ссылка), чтобы действие читалось как редактирование.

## Risks / Trade-offs

- **Коррелированные подзапросы в SELECT на больших таблицах `Call`** — приемлемо на текущем масштабе; индексы на `call.organization_id`, `call.scheduled_at`, `call.made_at` минимизируют стоимость. Пагинация — вне скоупа (Non-Goal).
- **Поиск по контактам через EXISTS** может быть медленнее на очень больших наборах контактов; параметризация и `LIKE '%term%'` без полнотекстового индекса — осознанный трейд-офф для корпоративной панели (тысячи записей, не миллионы).
- **Все контакты в HTML сразу** увеличивают размер страницы на крупных клиентах; для ~десятков контактов на организацию это дешевле AJAX-ленивости по сложности и надёжности.
- **Сортировка по датам с NULL** даёт смешанные результаты — митигировано правилом «без даты — в конец», что отражено в спеке (Scenario «организации без запланированных звонков в конце»).
- **Заголовки сортировки без стабильного вторичного ключа** могут «прыгать» при равных датах — вторичное `o.name ASC` всегда добавляется в ORDER BY.
