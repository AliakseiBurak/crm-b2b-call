# Design: reconcile-specs-with-prd

## Context

`docs/source/PRD.md` (349 строк) — исходный продукт-документ B2B Call CRM. Перед
его удалением (переход к OpenSpec как единственному источнику истины) необходимо
убедиться, что 10 существующих спецификаций возможностей полностью и корректно
отражают требования PRD, и зафиксировать разрешение внутреннего противоречия PRD
о ролях.

Текущее состояние:

```
┌────────────────────────────────────────────────────────────────────┐
│                          docs/source/PRD.md                       │
│  §1.1 описание   §2.1–2.12 модель   §3.1–3.7 сервисы              │
│  §4.1–4.5 API    §5 UI              §6 стек/безопасность          │
│  §7 NFR          §8 план            §9 Symfony-компоненты         │
└───────┬──────────────┬───────────────┬──────────────┬─────────────┘
        │ сверка        │               │              │
        ▼               ▼               ▼              ▼
┌───────────────┐ ┌─────────────┐ ┌─────────────┐ ┌──────────────┐
│  10 specs     │ │ ADR-0001–4  │ │ project.md  │ │ config/AGENTS│
│ (opened ···)  │ │ (доступ)    │ │ (цели/стек) │ │ (контекст)   │
└───────────────┘ └─────────────┘ └─────────────┘ └──────────────┘
        │
        ▼  этот change
  reconcile: разойтись по поведению (2 дельты) + ADR-0005
```

## Goals / Non-Goals

**Goals:**
- Каждая спецификация корректно отражает PRD (матрица сверки ниже).
- Разрешено противоречие PRD о ролях через ADR-0005.
- Поведенческие дельты только там, где требования реально меняются.

**Non-Goals:**
- НЕ удаление PRD и строк-источников «PRD.md §…» (это change
  `remove-prd-sources`).
- НЕ добавление новых возможностей (users, NFR) — только фиксация решений
  (ADR-0005; отложенные пробелы — ADR-0006 в change
  `openspec-single-source-of-truth`).
- НЕ переписывание ADR-0001–0004 (выполняется в
  `openspec-single-source-of-truth`).

## Decisions

**D1. Дельта-спецификации только для реальных изменений поведения.**
`access-control` и `email-campaigns` получают `# @openspec: MODIFIED` дельты.
Остальные 8 возможностей — без дельт: изменение только прозы (строка-источник)
не является изменением поведения и обрабатывается в change
`remove-prd-sources`.

**D2. Роли — фиксированный enum (разрешение противоречия PRD).**
PRD §2.10/§3.7 задают роли как enum (admin, manager, operator); §4.5 вводит
CRUD `/api/roles`. Существующие спецификации и ADR-0001–0004 построены на enum.
Решение: набор ролей фиксирован, Roles CRUD не реализуется → ADR-0005.
Альтернативы рассмотрены: динамические роли потребовали бы пересмотра модели
доступа (ADR) и не имеют требований в PRD, кроме противоречивого §4.5.

**D3. Рассылки — в рамках организации.**
PRD §2.6 `EmailCampaign.organization_id` не отражён в спецификации. Правило
«Пакетная рассылка по группам контактов» дополнено: рассылка создаётся в рамках
организации и привязана к ней. Альтернатива (рассылка без привязки к
организации) противоречит PRD §2.6.

**D4. `contacts`: удаление контакта — обоснованное расширение.**
Спецификация обещает удаление контактов; PRD §4.2 не содержит DELETE-эндпоинта,
но §3.2 («Управление контактами») допускает управление. Изменений не требуется,
расширение фиксируется в матрице.

**D5. Сверка: 8 возможностей соответствуют PRD без правок.**
Матрица ниже подтверждает полное покрытие §2, §3, §4.1–4.4 существующими
спецификациями.

## Risks / Trade-offs

- [Порядок изменений] -> Дельты ссылаются на ADR-0005; ADR создаётся в этом же
  change до применения. Удаление PRD — только после `remove-prd-sources`.
- [Переписывание ADR-0001–0004] -> Схема OpenSpec считает ADR неизменяемыми;
  пользователь явно выбрал переписывание контекста — выполняется осознанно в
  change `openspec-single-source-of-truth` и фиксируется там.
- [Потеря требований при удалении PRD] -> Матрица сверки + ADR-0006
  (реестр отложенных пробелов) гарантируют, что ничто не теряется молча.

## Migration Plan

1. Создать ADR-0005 (`/workspace/adr/0005-roles-fixed-enum.md`) и manifest
   `adr.md` в change.
2. Создать tasks.md; применить change (реальных файловых правок, кроме ADR,
   change 1 не требует — дельты синхронизируются при архивации).
3. Синхронизировать дельты в основные спецификации и заархивировать change.
4. Продолжить changes 2 и 3 в установленном порядке.
