## Context

Сущность Contact содержит неиспользуемые поля `contactType` (enum ContactType) и `contactPerson`. Таблица адресатов рассылки не предоставляет навигации между contact/organization. Нет способа увидеть ошибки рассылок на странице контакта и сбросить статус `failed` получателя.

См. proposal.md — Why.

## Goals / Non-Goals

**Goals:**
- Упростить сущность Contact, удалив неиспользуемые поля
- Обеспечить навигацию между contact/organization из таблицы адресатов
- Предоставить возможность просмотра и сброса ошибок рассылок на странице контакта
- Показать связанные контакты в форме редактирования организации

**Non-Goals:**
- Изменять логику отправки рассылок (MailingService, worker)
- Добавлять новые статусы получателей
- Изменять модель доступа (ADR-0005–0008)

## Decisions

### 1. Таблица ошибок на форме редактирования контакта

**Решение**: Разместить таблицу ошибок под формой редактирования контакта на `GET /contacts/{id}/edit`.

**Альтернативы**:
- Отдельная страница `GET /contacts/{id}` — отклонена: пользователь просил обойтись без страниц просмотра
- Модальное окно — отклонено: пользователь указал что модальное окно не подходит

**Обоснование**: Форма редактирования — единственная страница контакта. Таблица ошибок рядом с формой позволяет сразу исправить контакт и сбросить ошибку.

### 2. Сброс bounced получателя

**Решение**: Кнопка «Сбросить» для bounced получателя ведёт на отдельную страницу подтверждения с предупреждением о бесмысленности сброса.

**Альтернативы**:
- Disable кнопки для bounced — отклонено: пользователь хочет чтобы кнопка вела на страницу подтверждения
- Обычный confirm() диалог — отклонено: недостаточно места для предупреждения

**Обоснование**: Bounced означает отклонение почтовым сервером. Повторная отправка вероятно приведёт к тому же результату. Страница подтверждения с подробным предупреждением помогает пользователю принять осознанное решение.

### 3. Навигация в таблице адресатов

**Решение**: Организация и контакт в таблице адресатов — кликабельные ссылки на `GET /organizations/{id}/edit` и `GET /contacts/{id}/edit` соответственно.

**Обоснование**: Прямые ссылки позволяют быстро перейти к редактированию организации или контакта для исправления ошибок.

### 4. Маршрут сброса получателя

**Решение**: `POST /campaigns/{id}/recipients/{recipientId}/reset` в CampaignController. Сброс только для статуса `failed`. Сброс `bounced` — через отдельный маршрут с подтверждением.

**Обоснование**: Разделение логики failed/bounced: failed — безопасен, bounced — требует предупреждения.

### 5. Удаление полей Contact

**Решение**: Миграция удаляет колونки `contact_type` и `contact_person`. Enum `ContactType` удаляется. Контроллер и форма обновляются.

**Обоснование**: Поля не используются в интерфейсе и бизнес-логике. Удаление упрощает сущность.

## Risks / Trade-offs

- [Потеря данных] → Данные из `contact_type` и `contact_person` удаляются безвозвратно. Это.acceptable, так как поля не используются.
- [Сломать существующие интеграции] → Если есть внешние системы, зависящие от этих полей. Миграция необратима.
- [Миграция на больших таблицах] → Если таблица contact очень большая, миграция может занять время. Рекомендуется выполнять в低активный период.

## Migration Plan

1. Выполнить миграцию для удаления колонок `contact_type` и `contact_person`
2. Удалить enum `ContactType`
3. Обновить ContactController и форму
4. Добавить новый маршрут resetRecipient в CampaignController
5. Обновить шаблоны
