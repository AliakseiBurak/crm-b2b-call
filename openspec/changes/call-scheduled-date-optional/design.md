## Context

- Форма звонка отправляется обычным POST на `app_call_create` (`/calls/new`),
  независимо от того, с какой страницы создания она открыта; при ошибке
  контроллер ре-рендерит `call/form.html.twig` со статусом 422.
- В create-режиме шаблон заполняет поля только из `call.scheduledAt`/
  `call.madeAt`/`call.notes` при `isEdit`, поэтому после ошибки введённое
  теряется (наблюдалось как «пустая форма на /calls/new»).
- Нативный `required` на `#scheduled_at` блокирует submit до сервера —
  серверные сообщения недостижимы (тот же класс проблемы, что исправлен в
  модалке контактов).
- Колонка `call.scheduled_at` уже nullable; миграция не требуется.

## Goals / Non-Goals

**Goals:**
- Пустая запланированная дата допустима при создании и редактировании.
- Только серверная валидация дат (без нативного блокирования отправки).
- После ошибки валидации форма восстанавливает введённые значения.

**Non-Goals:**
- Изменение правил «дата не может быть в прошлом» и формата ввода/вывода.
- Изменение статистики дашборда (waiting-бакеты уже NULL-safe).
- AJAX-отправка полной формы звонка (остаётся обычный POST).

## Decisions

- **Снять `Assert\NotNull` c `Call::$scheduledAt`; пустую строку трактовать
  как null** (applyRequest уже так парсит). Альтернатива — условная
  валидация в контроллере — отклонена: ограничение принадлежит сущности,
  а правило «не в прошлом» остаётся в контроллере для непустых значений.
- **Восстановление значений через существующую переменную `$call`:**
  applyRequest уже наполняет entity из запроса до валидации; шаблон в
  create-режиме читает значения из `call` независимо от `isEdit`
  (`scheduledAtValue` и поля made_at/notes/contact без guard'а `isEdit`).
  Альтернатива — флеш-сессия с введённым вводом — отклонена как избыточная.
- **Убрать только нативный `required`** у `#scheduled_at`; подсказки формата
  и серверные сообщения остаются источником обратной связи.

## Risks / Trade-offs

- [Существующие тесты фиксируют старое поведение «пустая дата = ошибка»]
  → переписать функциональные и e2e сценарии в рамках этого изменения.
- [Звонок одновременно без обеих дат] → допустим по спеке (звонок без дат
  не попадает ни в один бакет); отдельного запрета не вводим.
