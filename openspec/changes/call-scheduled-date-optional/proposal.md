## Why

Менеджер не может создать проведённый звонок, зная только фактическую дату:
форма требует запланированную дату на уровне браузера (нативный `required`
блокирует отправку до серверной валидации), а сервер считает пустую
запланированную дату ошибкой. Пользователь видит либо немое блокирование
отправки, либо пере-рендер формы по адресу /calls/new без введённых данных —
без понятного сообщения.

## What Changes

- **BREAKING**: Запланированная дата звонка (`scheduled_at`) становится
  опциональной: пустое значение больше не ошибка «Дата звонка обязательна
  для заполнения». Звонок можно создать, заполнив только фактическую дату.
- Правило «запланированная дата не может быть в прошлом» сохраняется для
  непустого значения; некорректный формат по-прежнему ошибка.
- Со страницы формы убирается нативный `required` поля даты: валидация —
  серверная (тот же принцип, что в модалках контактов/звонка).
- Форма создания после ошибки валидации сохраняет введённые пользователем
  значения (даты, контакт, заметка) вместо сброса к пустой форме.

### Modified Capabilities

- `calls/crud`: требование «Менеджер планирует звонок» — запланированная
  дата опциональна; сценарий «Ошибка валидации при создании» (пустая дата)
  заменяется сценарием создания с только фактической датой; добавляется
  сценарий сохранения введённых значений при ошибке валидации.

## Impact

- `src/Entity/Call.php` — снятие `Assert\NotNull` с `scheduledAt`.
- `src/Controller/CallController.php` — applyRequest: null допустим.
- `templates/call/form.html.twig` — убрать `required`; восстановление
  введённых значений в create-режиме после ошибки.
- Тесты: функциональные (`CallControllerTest`) и e2e (`calls-crud.spec.ts`)
  сценарии «пустая дата = ошибка» переписываются под новое поведение.
- Миграция БД не нужна: колонка `call.scheduled_at` уже nullable.
