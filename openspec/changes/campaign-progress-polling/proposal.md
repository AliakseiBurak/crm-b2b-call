## Why

Во время отправки рассылки фоновая команда обрабатывает получателей, но
статистика в списке рассылок («x из y» в колонке «Статистика») и статусы
отправления на странице «Адресаты» обновляются только после перезагрузки
страницы. Менеджер не видит прогресс отправки в реальном времени и вынужден
обновлять страницу вручную.

Нужно автоматическое обновление этих данных без перезагрузки. Канал событий
между процессом отправки (CLI-команда / Symfony Scheduler) и веб-процессом
(php-fpm) невозможен — память процессов не пересекается, поэтому прогресс
извлекается polling'ом напрямую из таблицы `campaign_recipients`, которую
пишет только процесс отправки.

## What Changes

- Новый endpoint `GET /campaigns/statuses` — статистика всех рассылок
  (`{ campaignId, delivered, total }`), агрегат по `campaign_recipient`.
- Новый endpoint `GET /campaigns/{id}/recipients/statuses` — статусы адресатов
  рассылки (`{ recipientId, status }`); 404 для несуществующей рассылки.
- Страница «Рассылки» (список): колонка «Статистика» («x из y») обновляется
  автоматически без перезагрузки страницы — опрос `GET /campaigns/statuses`
  каждые 1.9 секунды.
- Страница «Адресаты»: статус отправления каждого адресата обновляется
  автоматически без перезагрузки страницы — опрос
  `GET /campaigns/{id}/recipients/statuses` каждые 1.1 секунды.
- DOM обновляется только при изменении значений.
- Команда отправки (`CampaignSendCommand`, `CampaignSendProcessor`,
  `MailingService`) не изменяется.

### Modified Capabilities

  без перезагрузки страницы (polling данных `campaign_recipient`).

## Impact

- Новый контроллер `App\Controller\CampaignProgressController` с двумя
  JSON-маршрутами (`/campaigns/statuses`,
  `/campaigns/{id}/recipients/statuses`).
- Новые методы `CampaignRecipientRepository`: агрегат статистики по всем
  рассылкам и список статусов адресатов рассылки.
- Обновлены `campaign/index.html.twig` и `campaign/recipients.html.twig` —
  клиентский JS с опросом каждые 1.9с и 1.1с соответственно.
